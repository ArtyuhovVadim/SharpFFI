# Список задач и исправлений (TODO)

## Генераторы кода (`SharpFFI.Generators`)

Задачи по устранению известных архитектурных замечаний и багов в Source Generators.

---

### 1. `FixedStringGenerator`: преждевременное снятие пиннинга (Dangling Pointer)
* **Проблема**: В сгенерированном коде пиннинг буфера может завершаться до окончания работы с полученным нативным указателем (выход из блока `fixed` до завершения операций чтения/записи/копирования).
* **Решение**: Гарантировать, что блок `fixed` охватывает все манипуляции с указателем, либо использовать `fixed` statement на уровне всей области видимости метода.

---

### 4. `FixedString`: согласованность конструкторов при переполнении буфера
* **Проблема**: Различные перегрузки конструкторов фиксированных строк (из `string`, `ReadOnlySpan<char>`, `ReadOnlySpan<byte>`) по-разному обрабатывают случай, когда длина входных данных превышает емкость буфера (одни перегрузки усекают данные, другие могут бросать исключение).
* **Решение**: Привести к единой документированной стратегии: либо строго выбрасывать `ArgumentOutOfRangeException`, либо усекать строку с обязательной записью нуль-терминатора в конец буфера.

---

### 5. `FixedStringGenerator`: публичный доступ к свойству `Length`
* **Проблема**: Свойство `Length` в сгенерированных фиксированных строках объявлено как `private`, из-за чего вызывающий код не может узнать реальный размер строки без ручного сканирования буфера.
* **Решение**: Сделать свойство `public readonly int Length { get; }`.

---

### 6. Утечка памяти в IDE из-за `Microsoft.CodeAnalysis.Location` в модели генератора
* **Проблема**: В record-структуре `FixedStringGenerationContext` хранится объект `Location`. Даже при переопределённых `Equals` и `GetHashCode` объект `Location` держит сильную ссылку на полное `SyntaxTree` внутри кэша Roslyn, что приводит к утечкам памяти в Visual Studio / Rider при длительном редактировании кода.
* **Решение**: Заменить `Location` в модели на легковесный DTO (`string FilePath`, `TextSpan SourceSpan`, `LinePositionSpan LineSpan`), либо генерировать диагностику на отдельном этапе пайплайна без сохранения `SyntaxTree`.

---

### 7. Отсутствие поддержки вложенных типов (Nested Structs)
* **Проблема**: Если тип с атрибутом `[FixedString]` или `[Handle]` объявлен внутри другого типа (`public struct Outer { public partial struct Inner; }`), генератор генерирует `Inner` на уровне пространства имён, что нарушает иерархию `partial` и приводит к ошибке компиляции.
* **Решение**: Рекурсивно собирать родительские `TypeDeclarationSyntax` и заворачивать сгенерированное объявление во внешние `partial struct/class Outer`.

---

### 8. `HandleGenerator`: возможность указывать базовый тип хендла и тип по умолчанию
* **Проблема**: В текущей реализации тип поля `Handle` захардкожен (сейчас `IntPtr`). В реальных interop-сценариях часто требуются 32-битные дескрипторы (`uint`, `int`), 64-битные (`ulong`), нативные указатели (`nint`, `nuint`), либо специализированные типы.
* **Решение**: 
  1. Добавить возможность явно задавать тип хэндла через атрибут (например, `[Handle(Type = typeof(uint))]` или `[Handle(typeof(nuint))]`).
  2. Определить дефолтный тип по умолчанию (например, `nint` / `IntPtr`, если тип не указан явно).
  3. Генерировать соответствующий тип поля, конструкторы, операторы приведения (`explicit`/`implicit`) и компараторы для выбранного базового типа.

---

### 9. Валидация дженерик-арности для `[FixedList]` и `[FixedArray]`
* **Проблема**: Генераторы `FixedListGenerator` и `FixedArrayGenerator` генерируют код структуры, рассчитанный строго на один параметр типа элементов (`T`). Если разработчик помечает атрибутом не-дженерик структуру (`public partial struct MyList;`) или структуру с несколькими типами (`<TKey, TValue>`), компилятор C# выдает ошибку несовпадения арности partial-деклараций.
* **Решение**: Добавить Roslyn-анализатор (диагностику `FFI0005`), проверяющий, что структура с `[FixedList]` или `[FixedArray]` является дженериком строго с одним параметром типа (`symbol.TypeParameters.Length == 1`).

---

### 10. Запрет модификатора `readonly` для изменяемых структур (`[FixedList]`)
* **Проблема**: Структуры с атрибутом `[FixedList]` обладают изменяемым внутренним состоянием (`_count`, методы `Add`, `Remove`, `Clear`, ref-возврат элементов). Объявление структуры как `readonly partial struct` бессмысленно, нарушает семантику типа и приводит либо к ошибкам компиляции мутирующих методов, либо к скрытому созданию защитных копий (defensive copies) со сбросом изменений при передаче по `in` / `readonly ref`.
* **Решение**: Добавить Roslyn-анализатор (диагностику `FFI0006`, аналогично существующей `FFI0002` для `ref struct`), запрещающий модификатор `readonly` на структурах с атрибутом `[FixedList]`. Реализовать соответствующий CodeFix для удаления `readonly`.

---

### 11. `FixedListGenerator`: возможность указывать тип счетчика длины (`_count`)
* **Проблема**: В текущей реализации поле `_count` всегда имеет тип `int` (4 байта). Для компактных структур с фиксированной емкостью (например, 8, 16 или 32 элемента) 4-байтовый счетчик создает избыточный оверхед по памяти и нарушает бинарный лейаут C-структур (где длина часто объявляется как `uint8_t` или `uint16_t`).
* **Решение**: 
  1. Добавить возможность указывать тип счетчика через параметр атрибута (например, `[FixedList(8, CountType = typeof(byte))]` или через специальный enum `FixedListCountType.Byte`).
  2. Валидировать, чтобы `Capacity` помещался в максимальное значение выбранного типа длины (например, для `byte` `Capacity <= 255`).
  3. Генерировать приватное поле соответствующего размера (`private byte _count;` или `private ushort _count;`), сохраняя при этом удобное свойство `public readonly int Count => _count;` для привычного использования в C#.

---

### 12. Поддержка современного форматирования строк (`IFormattable`, `ISpanFormattable`, `IUtf8SpanFormattable`)
* **Проблема**: Строковые типы (генерируемые `FixedString` и примитивы `SharpFFI.Primitives`: `NativeUtf8CString`, `Utf8CString`, `ReadOnlyUtf8CString`, `Utf8StringView` и др.) поддерживают только стандартный `ToString()`. При использовании в строковой интерполяции (`$"{str}"`), `string.Create`, `Utf8.TryWrite`, `StringBuilder.Append` или логировании всегда происходит аллокация управляемой строки `System.String`, а также отсутствует возможность прямого безаллокационного форматирования в `Span<char>` и `Span<byte>`.
* **Решение**:
  1. **`IFormattable`**: Реализовать метод `string ToString(string? format, IFormatProvider? formatProvider)` (с поддержкой стандартных форматов и провайдеров).
  2. **`ISpanFormattable`** (начиная с .NET 6 / .NET Standard 2.1 при наличии полифила): Реализовать `bool TryFormat(Span<char> destination, out int charsWritten, ReadOnlySpan<char> format, IFormatProvider? provider)` с прямой декодировкой UTF-8 байтов в `destination` без промежуточных аллокаций.
  3. **`IUtf8SpanFormattable`** (.NET 8+): Реализовать `bool TryFormat(Span<byte> utf8Destination, out int bytesWritten, ReadOnlySpan<char> format, IFormatProvider? provider)` для прямого копирования UTF-8 байтов в целевой буфер без транскодирования в UTF-16.
  4. Внедрить генерацию этих интерфейсов и методов в `FixedStringGenerator`, а также поддержать их в строковых примитивах библиотеки `SharpFFI.Primitives`.
